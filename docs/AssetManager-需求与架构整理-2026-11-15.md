## 1. 讨论还原

四轮问答，主线是一条：**「怎么保证不卡、不涨、不崩」**。按轮次还原核心主张，最后统一批注。

### 1.1 第一轮 · 怎么保证用起来不卡

原结论一句话：**Rust 负责「看」和「算」，WebView 只负责「画」**。五根支柱：

1. **图片缩略图三级缓存**
   - 一级：Windows 原生缩略图（`IShellItemImageFactory`），Explorer 看过的图可能直接命中，零解码
   - 二级：自建持久缓存，key = `sha256(路径 + mtime + 尺寸)`，容量上限 + LRU
   - 三级：只预取视口附近（约 ±1 屏），绝不整目录预生成
2. **缩略图字节不走 IPC**：Tauri IPC 会把 `Vec<u8>` 序列化成 JSON 数字数组，5 MB 图能膨胀成 20 MB JSON 直接卡死。改注册自定义协议（`thumb://`），前端 `<img src>` 直取，解码交给 WebView 合成线程
3. **Blender 不启软件拿预览**：`.blend` 内部有 TEST block 存了预览图，解析文件块即可取出，参考 Go 的 `blendpreview`
4. **虚拟滚动是底线**：只渲染视口内 20–50 个节点，10 万条列表可稳定 59.7 FPS
5. **元数据进 SQLite 不进 JSON**：JSON 在万级就成瓶颈，SQLite 百万行 B-tree 查询亚毫秒

### 1.2 第二轮 · 多平台化

- Tauri 2 本身就是跨平台基座，Rust 核心逻辑天然复用
- **最大坑是缩略图**：`thumb-rs` 支持 macOS（QuickLook）与 Windows（IShellItemImageFactory），**不支持 Linux**
- Linux 只能自建管线（`libvips` / `image` crate），因为桌面环境碎片化，没有统一系统 API
- 应对：定义 `ThumbnailProvider` trait，每平台一个实现，业务层不感知
- `.blend` 解析是纯 Rust（`blend` / `blend-rs`），零系统依赖，最省心
- 文件监听用 `notify`，但路径规范化（大小写、分隔符、Unicode）仍需抽象成 `FileSystemAdapter`
- 移动端建议暂缓

### 1.3 第三轮 · 缓存占多少空间

- 10 万文件：256px 缩略图 ≈ 1.5 GB，512px ≈ 4.5 GB，SQLite 元数据 ≈ 30 MB
- 三件套：**容量上限 + LRU 淘汰 + 按需生成**
- **元数据不参与淘汰**（删了要重扫，代价高），只有可再生成的二进制缓存才淘汰
- 默认上限建议 1–2 GB，用户可调

### 1.4 第四轮 · 百万级

- 存储不是主要矛盾，**扫描策略、深分页查询、缩略图限流**才是
- SQLite 必须显式配置：`WAL` / `synchronous=NORMAL` / `cache_size=-64000` / 四个索引
- 分页用 **keyset pagination**（`WHERE id > ?`），`OFFSET` 深翻会越来越慢
- 文件夹树与文件列表**分开存**：树只存目录节点，列表按 `parent_dir` 查
- 首扫必须后台、可中断、可增量、只入元数据不生成缩略图
- 三个坑：inotify watch 上限（别递归监听全库）、路径索引磁盘开销、扫描与浏览的磁盘 IO 争抢

### 1.5 我的批注（讨论没说到的地方）

| # | 讨论的说法 | 我的修正 |
|---|---|---|
| 1 | 「第一次扫描百万文件元数据几分钟入库」 | 偏乐观。NTFS 枚举 100 万条目在 SSD 上约 2–6 分钟、机械盘 10–30 分钟，**再叠加每文件一次 stat**。要按「分钟级 + 可中断 + 断点续扫」设计，别向用户承诺秒级 |
| 2 | 「用 `thumb-rs` 走系统快车道」 | 系统缩略图**质量不可控**（很多格式拿到的是 96×96 位图），且**只在 Explorer 看过才有**。它只能当「先出图占位」的一级，不能当最终质量 |
| 3 | 「3D 用 LOD 渐进加载」 | 混了两种东西：`.blend` **不可能**交互预览（没有运行时），glTF 可以。两者要分开承诺（§2.5） |
| 4 | 「`.blend` 里嵌了缩略图」 | 只说了一半。①只有保存时勾了 `Save Preview Images` 才有；②尺寸通常 **128×128**；③3.0+ 默认 zstd 压缩，要流式解压到 TEST block。所以「128px 放大＝模糊」是常态，界面要把它设计成正常态 |
| 5 | 全程只有「快」，没有「素材语义」 | 对标 Eagle 之后这条更致命：Eagle 的手感 80% 来自**标签 + 智能文件夹 + 瀑布流 + 拖拽**，性能只是它的短板。只做快 = 没有人搬家的理由（§2.2） |

## 2. 可行性评估

### 2.1 结论

**技术上完全可行，而且成本比想象低；难点从「定位」转移到了「两件硬仗」：**

1. **百万级流畅** —— 结构性工程，不是调参数
2. **Eagle 手感还原度** —— 标签/智能文件夹/拖拽/采集这四件事，缺一件用户就觉得「不如 Eagle」

我上一版说「最大风险是定位」，现在定位拍死了（对标 Eagle），所以风险清单换成上面两条。**这不是好消息也不是坏消息，只是把仗打到了正确的地方。**

### 2.2 Eagle 拆解：它凭什么好用，又为什么在百万级会卡

对标要知道对手的结构，否则容易抄错东西。

**它凭什么好用（这些必须抄，抄的是体验不是实现）**

| 能力 | 为什么关键 |
|---|---|
| 瀑布流（justified，行内等高、按宽高比排） | 素材浏览的唯一正确布局。等高网格会把竖构图压扁，视觉判断失效 |
| 标签（多标签 / 标签组 / 颜色标签） | 素材的第二套坐标系。文件夹只能套一层，标签能交叉 |
| 智能文件夹（保存的查询） | 整理一次，永远有效。这是 Eagle 最被低估的功能 |
| 拖拽到 PS / AI / Blender | 素材库的出口。没有出口的库是坟墓 |
| 浏览器插件采集 | 让「入库」成本降到一次点击，库才长得起来 |
| 评分 / 注释 / 来源 URL / 颜色筛选 | 找回素材的 4 条捷径 |

**它为什么在百万级会卡（社区常见反馈 + 结构推断，需实测复核）**

| 结构性原因 | 后果 | 我们的对策 |
|---|---|---|
| Electron 渲染进程 + 每素材一个 `.info` 目录（约 3 个文件） | 100 万素材 ≈ **300 万小文件**，NTFS 枚举、杀软扫描、备份、同步全部变慢 | **索引式为主**：文件留在原地，库里只有一个 DB + 集中缩略图（§2.3） |
| 每素材一个 `metadata.json`，启动/切换依赖大量小文件读取 | 首屏随库增大线性变差 | 元数据全在 SQLite 单文件，首屏只查一页（§4.2） |
| JSON 全量加载进内存 | 十万级就开始吃 1 GB+ | 分页 + keyset，内存恒定 200–500 MB（§5.1） |
| 缩略图生成与 UI 同进程抢资源 | 导入时整机卡住 | Rust 侧独立线程池 + 优先级队列 + 限流（§4.4） |

> 一句话：**Eagle 的库结构是为「可迁移、可手动管理」设计的，不是为百万级设计的。** 我们不能既抄它的目录结构又要求它快。
>
> 注意：上表是结构推断，**开工前必须用 Eagle 实测一份基线**（§5.3），否则我们的「更快」没有分母。

### 2.3 库结构：索引式 vs 托管式（第一个必须拍的决定）

| | 索引式（推荐默认） | 托管式（Eagle 同款） |
|---|---|---|
| 文件在哪 | 留在用户原有目录，库只存索引 | 导入时复制进 `.library/images/<id>/` |
| 百万级代价 | 1 份文件 + 1 个 DB + 集中缩略图 | **2 份文件 + 300 万小文件** |
| 迁移成本 | 零（不搬文件） | 大（导入要等几小时） |
| 手动管理 | 用户在 Explorer 里改了，我们靠 mtime 跟上 | 库目录不能乱动 |
| 换软件 | 随时走，文件本来就在原地 | 得导出 |
| 缺点 | 文件被外部改名/移动后要重定位 | 库是黑盒，但对普通用户更省心 |

**我的建议：索引式做默认，托管式做成「Eagle 兼容模式」给要迁移的人。**
理由很直接：你的主场是百万级，托管式在这个量级上是自找的（存储翻倍 + 小文件灾难）。

### 2.4 真正的难度排序

| 难度 | 事项 | 为什么难 | 什么时候必须解决 |
|---|---|---|---|
| ★★★★★ | 百万级流畅（帧预算 / 调度 / 长任务切分） | 每一处「顺手写」都会在百万级放大成卡顿；要全程有性能纪律 | M0 就定死，后期补不回来 |
| ★★★★☆ | Eagle 手感还原（瀑布流 + 智能文件夹 + 拖拽） | 差一点用户就觉得「不如原来的」 | M1 |
| ★★★★☆ | 素材语义（标签 / 引用 / 去重 / 检索） | 没有正确答案，只有取舍；做错要迁移数据 | M1 前定死 schema |
| ★★★☆☆ | 缩略图管线（多格式 × 质量 × 限流） | 四维交叉，且「合法失败」很多 | M1 |
| ★★★☆☆ | 重格式预览（PSD/AI/Sketch/PDF） | 解析库各有坑，失败率高 | M2 |
| ★★☆☆☆ | 跨平台缩略图差异 | 三个实现，工作量明确 | M2 |
| ★★☆☆☆ | 3D / `.blend` | 价值高但不是主场 | M4 |

### 2.5 三个必须提前承认的天花板

写进 PRD，也写进「关于」页，避免以后被当成 bug：

1. **`.blend` 只能静态预览，不能交互。**
   原因：Blender 运行时不可嵌入，几何是 DNA 结构化的内存镜像，不含可渲染场景描述。
   能做：TEST block 缩略图（≤128px，可能没有）+ 文件头元数据（版本、是否 packed）。
   真做交互预览只有两条路，都贵：调 Blender CLI 导出 glb（要求用户装 Blender），或自研 DNA 解析器（半年起）。

2. **重格式预览有成本上限。** `PSD`（合成图可读、图层要额外解析）、`AI`（PDF 兼容流）、`Sketch`（zip + JSON，可读）、`Figma`（需 API）—— 成功率不会是 100%，目标 ≥ 95% 且失败有明确图标。

3. **首扫是分钟级。** 100 万条目枚举 + stat，SSD 2–6 分钟、机械盘 10–30 分钟。UI 上要显示「已扫 43 万 / 预计还需 3 分钟」，而不是转圈。

### 2.6 明确不做的（省返工）

- ❌ 抢系统图片默认关联（装完改掉用户双击行为 = 卸载理由）
- ❌ 移动端（文件系统模型不同，收益低）
- ❌ 素材编辑（不裁剪不转码成第二个产品；单条导出/转换可以）
- ❌ 全库递归实时监听（百万级必爆 watch 上限，改「活跃目录监听 + 定时增量」）
- ❌ 云同步 / 团队协作（现阶段不做，schema 留 `owner` / `updated_at` 以便日后加）

## 4. 架构方案

### 4.1 分层

```
┌──────────────────────────────────────────────────┐
│ 前端 (React + TS)                                 │
│  虚拟滚动 · 只持 200–500 行 · <img src="thumb://"> │
└────────────────┬─────────────────────────────────┘
                 │ invoke（元数据）/ 自定义协议（字节）
┌────────────────▼─────────────────────────────────┐
│ Rust 核心                                         │
│  ┌──────────┬──────────┬──────────┬───────────┐  │
│  │ Scanner  │ Indexer  │ Thumb    │ Resolver  │  │
│  │ 扫描/监听 │ SQLite   │ 管线/队列 │ 引用/去重  │  │
│  └──────────┴──────────┴──────────┴───────────┘  │
│  ┌────────────────────────────────────────────┐  │
│  │ 平台薄层 ThumbProvider / FsAdapter          │  │
│  │ Win: IShellItemImageFactory + WIC           │  │
│  │ macOS: QLThumbnailGenerator                 │  │
│  │ Linux: image / libvips                      │  │
│  └────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────┘
```

铁律四条（前三条来自讨论，第四条是我加的，百万级必须）：

1. **字节永不走 IPC**，只走自定义协议
2. **重活永不进 UI 线程**，也不进 WebView 的 JS 主线程
3. **索引是派生数据**，任何时刻可删可重建，真相在文件系统
4. **任何前端操作都不许「一次查全库」** —— 查询必须带 limit，渲染必须有窗口，批量必须分片

### 4.2 索引层：SQLite 设计

**PRAGMA（`db.rs::open()` 里一次设好）**

```sql
PRAGMA journal_mode = WAL;        -- 扫描写入与前端查询不互斥
PRAGMA synchronous  = NORMAL;     -- WAL 下安全且快
PRAGMA cache_size   = -64000;     -- 64 MB 页缓存
PRAGMA temp_store   = MEMORY;
PRAGMA mmap_size    = 268435456;  -- 256 MB
```

**为什么 trigram**：素材名大量中文且常被「中间截取」搜索（搜「贴图」要命中「石材贴图_04」）。`trigram` 支持任意子串，代价是索引体积 2–3 倍 —— 百万级可接受，换来「搜得到」这个最基本的能力。

#### 4.2.1 分页（keyset，不用 OFFSET）

```sql
-- 第一页
SELECT id, name, ext, kind, width, height, thumb_key FROM assets
WHERE missing = 0 AND kind IN (?1) ORDER BY mtime DESC, id DESC LIMIT 200;

-- 下一页（带上一页最后一条的排序键）
SELECT ... WHERE (mtime, id) < (?1, ?2) AND ... ORDER BY mtime DESC, id DESC LIMIT 200;
```

前端永远只持「当前页 + 预取页」（200–500 行）。**深翻第 500 页与第 1 页耗时同量级**，这是 OFFSET 做不到的。

#### 4.2.2 计数不能每次都 COUNT

侧栏「共 128 万」`COUNT(*)` 在百万级要几百毫秒到几秒。对策：

- 维护 `meta` 表存近似计数（扫描时累加），显示 `≈128 万`
- 精确计数只在用户点开某一分类时算，且结果缓存（`counts.version` 失效即重算）
- 前端显示带 `≈` 是诚实做法，比转圈 3 秒好

#### 4.2.3 智能文件夹的查询 DSL

白名单字段，后端拼 SQL，不接原始 SQL：

```json

  "kind": [0, 3],
  "ext": ["png", "psd"],
  "tags_any": ["石材"],
  "size_min": 1048576,
```

### 4.3 扫描层

| 要求 | 实现 |
|---|---|
| 后台 | 独立线程 + `scan://progress` 事件；前端 3px 进度条 + 「已扫 N / 预计还需 M」+ 取消 |
| 可中断 | `AtomicBool` 每 500 条检查；取消后已入库数据保留 |
| 断点续扫 | `dirs.scanned_at` 与 `mtime` 比对，只重扫变化目录 |
| 防环 | 记录 `(volume_serial, file_id)`，跳过 junction / symlink 回环（Windows 上很常见） |
| 长路径 | 一律 `\\?\` 前缀（>260 字符），`std::fs` 在 Windows 需显式加 |
| 写库节奏 | **500 条一个事务** commit，别一条一 commit（百万级会慢 10 倍以上） |
| IO 谦让 | 扫描线程降优先级；缩略图生成限流；避免用户感觉「硬盘被吃满」 |

扫描顺序：广度优先（先让用户看到目录结构），并允许「先扫这几个目录」的手动优先队列。

监听：`notify` 只挂**当前展开目录 + 库根**，其余靠定时增量（默认 30 分钟或手动）。

### 4.4 缩略图层（全项目最重的新代码）

**Provider trait**

```rust
pub struct ThumbSpec { pub px: u32, pub quality: u8 }

pub trait ThumbProvider: Send + Sync {
    fn try_fast(&self, path: &Path, spec: ThumbSpec) -> Option<RgbaImage>;
    fn render(&self, path: &Path, spec: ThumbSpec) -> Result<RgbaImage, ThumbError>;
    fn supports(&self, ext: &str) -> bool;
}
```

| 平台 | try_fast | render |
|---|---|---|
| Windows | `IShellItemImageFactory`；RAW/HEIC 走 WIC | `zune-jpeg` / `image` / `libvips` |
| macOS | `QLThumbnailGenerator` | 同上 |
| Linux | `~/.cache/thumbnails`（仅图片/视频） | `libvips` 优先，退回 `image` |

**管线（「不卡」的真正实现）**

```
滚动 → 请求可见 N 张 → 三档优先级队列（可见 > 预取 > 后台补全）
   ↓
固定 4–8 线程（默认 min(核数/2, 6)）
   ↓
命中缓存？→ 回 / 否则 try_fast → 质量不足再 render → 编码 WebP → 原子写盘 → 回
   ↓
滚出视口的待办 → 打取消标记（已开始跑完，未开始不做）
```

**缓存布局**

- key = `xxh3(路径 | mtime | size | spec_version | px)` → 16 字节 hex
- 路径：`<data>/cache/thumbs/<前2>/<后2>/<key>.webp`（两级分桶，避免单目录百万文件）
- 尺寸只两档：**256**（列表/瀑布流）与 **512**（详情，按需）
- WebP q=78：256px 约 12–18 KB，512px 约 40–60 KB
- 上限默认 **2 GB**，LRU 按 `last_access`（记在 DB 小表，别读文件 atime，不可靠）
- 到 90% 后台清到 70%，不阻塞前台

**三态占位（手感的另一半）**

| 态 | 显示 |
|---|---|
| 排队中 | 骨架块（2% 墨底）+ 右上角类型小标，**占位尺寸已按真实宽高比算好**（不跳行） |
| 低清已出（fast 路径） | 低清图 + 4px 模糊，高清到位原地替换（**不闪白**） |
| 失败 | 格式图标 + 弱色「无法预览」，右键可重试 |

> 「不闪白」和「不跳行」这两条，比多 10 帧更影响「流畅」的主观感受。

### 4.5 传输层 `thumb://`

- Tauri 2 自定义协议；Windows 上落在 `http://thumb.localhost/<key>?s=256`
- 响应头 `Cache-Control: public, max-age=31536000, immutable`，让 WebView 再缓存一层（免费第四级）
- 只接受 hex key，不接受任意路径（防穿越）
- 未命中返回 404 + 触发后台生成；前端 `<img onerror>` 换骨架，**绝不同步等生成**

### 4.6 前端性能纪律（百万级的真章）

| 纪律 | 做法 | 违反的后果 |
|---|---|---|
| 虚拟滚动 | 只渲染视口 + 2 行缓冲 | 1 万 DOM 就掉到 30 帧 |
| 行虚拟化 + 列固定 | 瀑布流按「行」虚拟，行内项固定 | 单格虚拟会让 justified 布局抖动 |
| 不整体重渲染 | 选中态用 `Set<id>` + 单项订阅，别把整个列表塞进一个 state | 点一下重渲染 500 条 |
| 固定宽高比占位 | 缩略图容器按 `width/height` 先撑开 | 图来了跳行，滚动位置乱跳 |
| 筛选延迟 | 输入用 `useDeferredValue` / 160ms 防抖，请求带代号丢弃过期响应 | 打字打一半出来旧结果 |
| 长任务切分 | 批量操作分片（每 200 个让出一帧） | 一次处理 5000 个 → 界面冻结 5 秒 |
| 动画只动 transform/opacity | 沿用 `springs.ts` 令牌 | 动 `width/height` 触发重排 |
| 图片解码不占主线程 | `decoding="async"` + 固定 `loading` 策略 | 大图解码抢帧 |

**帧预算（16.7 ms/帧）**

| 阶段 | 预算 |
|---|---|
| JS（含虚拟滚动计算） | ≤ 6 ms |
| Style + Layout | ≤ 4 ms |
| Paint + Composite | ≤ 6 ms |

滚动时任何一项超预算，都在 DevTools 里记一笔「性能债」，别攒到 M3。

### 4.7 3D / 重格式（M4，不是主场）

**`.blend` 要点（要用时的全部知识）**

| 项 | 内容 |
|---|---|
| 魔数 | 前 7 字节 `BLENDER` |
| 指针宽度 | 第 8 字节 `_` = 4 字节，`-` = 8 字节 |
| 字节序 | 第 9 字节 `v` = 小端，`V` = 大端 |
| 版本 | 第 10–12 字节，如 `405` |
| 压缩 | gzip 头 `1F 8B`（旧）或 zstd 头 `28 B5 2F FD`（3.0+） |
| 块头 | `code(4) + len(4) + old_ptr(4/8) + sdna(4) + count(4)` |
| 预览块 | `code == "TEST"`：`width(4) + height(4) + RGBA 原始像素`（自下而上，要翻转） |

1. 读头 12 字节判断压缩与指针宽度
2. 压缩文件**流式解压，读到 TEST 就停**（`.blend` 常几百 MB 到几 GB，不能整文件解压）
3. 尺寸常 128×128；放大到 256 用 Lanczos，接受模糊，别标「高清」
4. 没有 TEST → `thumb_state = unsupported`，显示格式图标，**不重试**
5. 只读 header + TEST + 大小，**不解析 DNA**

**重格式分级**

| 格式 | 做法 | 成功率预期 |
|---|---|---|
| PSD | 读合成图（`psd` crate 或 WIC） | ~98% |
| AI | 内部是 PDF 兼容流，按 PDF 渲染 | ~85%（旧版 EPS 存法不行） |
| Sketch | zip + JSON 预览图 | ~95% |
| PDF | 首页渲染 | ~99% |
| FBX/USD/ABC | 只元数据 + 图标 | — |

### 4.8 崩溃安全与可重建

FontManager 的 `state.json` 事故（1.7 MB 被写回 16 KB）在 DB 上更致命，开头就定死：

1. **DB 是派生数据**：删了只丢标签/评分/收藏，文件不动 → 设置页必须有「重建索引」，文案讲清代价
2. **坏库改名留证**：`index.corrupt-<ts>.db` 保留，不静默删
3. **退出时 `PRAGMA wal_checkpoint(TRUNCATE)`**
4. **用户创造的数据单独备份**：`tags` / `asset_tags` / `collections` / `note` / `rating` 每 24 小时导出 `userdata-<ts>.json`（几十 KB），DB 挂了能回灌
5. **扫描中断标记**：`scan_incomplete=1`，下次续扫而不是重置

### 5.1 硬指标

写进 PRD 当验收，不是愿望。测试库：**100 万素材（其中 60 万图片、30 万小文件、10 万 PSD/工程）**。

| 指标 | 目标 | 测法 |
|---|---|---|
| 冷启动到首屏有内容 | ≤ 800 ms | 日志时间戳 |
| 首屏查询 | ≤ 200 ms | DB 打点 |
| 滚动帧率（10 万 / 100 万库） | ≥ 55 FPS，无 100ms 以上长帧 | DevTools Performance |
| 滚动时缩略图**闪白次数** | **0** | 录屏逐帧 |

| 点击到视觉反馈（锚点变色） | ≤ 50 ms | 手动 + 录屏 |

| 搜索响应（100 万库，含中文子串） | ≤ 120 ms | 打点 |
| 单张缩略图 p95（4K JPEG） | ≤ 120 ms | 管线埋点 |
| 缩略图成功率 | ≥ 98% | `thumb_state` 统计 |
| 首扫 100 万（SSD，仅元数据） | 2–6 分钟，可中断 | 实测报告 |

| 批量打标 5000 个 | ≤ 3 秒且有进度 | 打点 |
| 深分页（第 500 页） | 与第 1 页 ±20% | keyset 验证 |

### 5.2 「流畅」的五个隐藏杀手

帧率只是其中一项。百万级下真正让人摔鼠标的是这五件事，**每一个都要在 M0 就定方案**：

| 杀手 | 症状 | 方案 |
|---|---|---|
| 缩略图闪白 | 滚动时一片白格子 | 三态占位 + 低清先出（§4.4） |
| 布局跳动 | 图加载完列表往下窜 | 按宽高比预先撑开（§4.6） |
| 筛选卡顿 | 打个字界面停 1 秒 | 防抖 + 过期响应丢弃 + 索引命中（§4.6） |
| 批量无反馈 | 点了没反应，以为没点上 | 分片执行 + 进度 + 可取消 |
| 计数转圈 | 侧栏「共 N 个」等 3 秒 | 近似计数 + 缓存（§4.2.2） |

### 5.3 开工前必做：Eagle 基线实测

**没有分母就没有「更快」。** 用同一个 100 万素材库（或 20 万可外推）测 Eagle：

### 6.3 图标 5 套（延续拼贴纸片风，母题换「叠片」）

| 图标 | 用途 | 母题 |
|---|---|---|
| `main` | 应用本体 / 任务栏 / 安装包 | 三张错位叠片 + 手写 `A`，白底板 |
| `pack` | 导出包 `.A-AssetManager` | 叠片 + 胶带封口，透明底 |
| `library` | 素材库文件夹（`.zam-folder.ico` 同类机制） | 文件夹里插一张露角相纸 |
| `asset3d` | 界面内 3D 类 ArtIcon（64px） | 线框三角面 + 纸片阴影 |
| `broken` | 缩略图失败 / 丢失资源 | 撕角纸片 + 一条折痕 |

硬约束（与 FontManager 完全一致，不用重新讨论）：

- `.ico` **必须七帧** 16/24/32/48/64/128/256，少一帧单测挂
- 图标字节变了要发 `SHCNE_ASSOCCHANGED`，否则 Explorer 拿旧缓存画
- 16/24px 单独校验可辨识（纸纹和手写字到 16px 会糊）
- 位图母版最大 256，512 是 Lanczos 放大
- **不抢系统文件关联**，只做库文件夹图标 + 界面内图标

### 6.4 光标（你点名要的那个）

直接复用 `BlinkCaretInput` + `design/primitives/blinkCaret.css`，**别重新实现**：

| 项 | 规格 |
|---|---|
| 形态 | 块状光标（不是竖条）：宽 = 字符 advance + 左右各 4px，圆角 3px |
| 高 | 字号 + 2px，垂直居中（13px 字 → 15px 块） |
| 颜色 | `--caret-blue`：深 `#4c8dff` / 浅 `#2f6bdb`，蓝底白字 |
| 闪烁 | 1.1s **硬切**（不是渐变）；`prefers-reduced-motion` 常亮 |
| 原生 caret | 隐藏（`caret-color: transparent`） |
| 中文 IME | 组合期间自动切回原生（`.is-composing`），否则候选框位置飘 |
| 不支持 | `password`（明文进镜像 DOM）；`textarea` 保持原生 |
| readOnly | `input[readonly] { caret-color: auto }` 兜底 |

要接入的输入框（共 8 处）：主搜索、快捷筛选、标签输入、批量重命名规则、智能文件夹命名、路径输入、右键菜单「打字即搜」、采集面板的 URL 输入。

### 6.5 与 FontManager 的有意差异

| 项 | FontManager | AssetManager | 理由 |
|---|---|---|---|
| 主角 | 字形（大字号样张） | 缩略图 | 内容形态不同 |
| 字号滑杆 | 有（8–96 八档） | **无**，改缩略图尺寸四档 | 图片不调字 |
| 行首锚点 | 列表/卡片内 | 瀑布流里改到**格内左上角** | 格子是独立单元 |
| 强调色 | 蓝 | 蓝（不变） | 品牌连续性 |

## 7. 优化建议 12 条（按 价值/成本 排）

| # | 建议 | 价值 | 成本 | 说明 |
|---|---|---|---|---|
| 1 | **把「不闪白 + 不跳行」当 M0 验收项** | ★★★★★ | 低 | 这两条比 +10 帧更决定主观流畅度，且一旦架构定了很难补 |
| 2 | **索引式库结构（文件不搬）** | ★★★★★ | 中 | 百万级下省掉一倍存储和 300 万小文件，是对 Eagle 的结构性超越 |
| 3 | **缩略图三态 + 队列取消** | ★★★★★ | 低 | 直接决定「用起来顺不顺」 |
| 4 | **智能文件夹取代手工整理** | ★★★★☆ | 低 | 一条 SQL + 一个侧栏项，整理效率翻倍 |
| 5 | **FTS5 trigram 中文子串搜索** | ★★★★☆ | 低 | 搜不到＝不存在。这条不能省 |
| 6 | **近似计数 + 缓存** | ★★★★☆ | 低 | 侧栏「共 N 个」转圈是大型库最廉价的卡顿源 |
| 7 | **索引可重建 + 用户数据单独备份** | ★★★★☆ | 低 | 避免 FontManager 的 state 事故重演 |
| 8 | **复用本地 API 做浏览器采集** | ★★★☆☆ | 低 | `api.json` + 令牌 + 端口复用，扩展端只写 UI |
| 9 | **精确去重 + 相似图（xxh3 + pHash）** | ★★★☆☆ | 中 | 素材库必然堆积重复 |
| 10 | **不抢文件关联，只做拖拽与发送到** | ★★★☆☆ | 极低 | 抢关联＝卸载理由 |
| 11 | **缓存占用可视化** | ★★★☆☆ | 低 | 用户才敢让它占 2 GB |
| 12 | **批量操作全部可撤销** | ★★★☆☆ | 中 | 先做「撤销上一次批量」就够 |

**不做**：全库递归监听、移动端、自研 `.blend` DNA 解析（M4 前）、在线素材市场。

## 8. 路线图

单人全职估，含自测与文档。**排序原则：性能地基先于功能**，因为性能是结构问题，功能可以后加。

| 阶段 | 内容 | 估时 | 验收 |
|---|---|---|---|
| **M0 流畅地基** | Tauri 2 骨架（照搬 FontManager）；设计令牌共享包；SQLite + migration；扫描器（元数据、可中断、断点续扫）；瀑布流/网格/列表 + 虚拟滚动；`thumb://` + 图片缩略图管线；`BlinkCaretInput`；**帧预算与性能埋点** | 3 周 | 100 万库：滚动 ≥55 FPS、闪白 0、跳行 0、首屏 ≤800ms |
| **M1 Eagle 手感** | 标签（含组/颜色）+ 文件夹 + 智能文件夹 + 评分/注释/来源 + 搜索（FTS5）+ 筛选（类型/颜色/尺寸）+ 排序 + 详情 + 批量（可撤销）+ 回收站 + 拖入/拖出 + 缓存设置 | 4 周 | 可当日常素材库用一整天不烦；能替代 Eagle 的日常路径 |
| **M2 采集与互操作** | 浏览器采集扩展（复用本地 API）+ Eagle 库迁移 + 重格式预览（PSD/AI/PDF/Sketch）+ 重复/相似检测 + 色板与颜色搜索 + 命令面板 | 3 周 | 采集→入库→找到→拖出，全链路闭环 |
| **M3 大库工程化** | 百万级实机压测与调优；多库；自动标签规则；缓存预算打磨；崩溃恢复演练；安装器路线 C + 9 语言 + 插件系统 + 更新 + 签名 | 2 周 | 对外可发布；压测报告达标 |
| **M4 扩展** | `.blend` 嵌入预览 / `.glb` 离屏渲染；引用关系与丢失检测；批量重命名；跨平台（macOS 优先） | 3 周 | 3D 库可出图；引用问题可一键回答 |

**M0 之前必须先做**（不做就是挖坑）：跑 §5.3 的 Eagle 基线、定 §4.2 的 schema、拍 §9 的七个问题。

## 10. 附录

### 10.1 与 FontManager 的关键差异（移植时最容易踩的坑）

| 差异 | FontManager | AssetManager | 影响 |
|---|---|---|---|
| 数据规模 | 5 千字族 | 万–百万素材 | JSON → SQLite 是必改项，不能沿用 `font-cache.json` 思路 |
| 单条重量 | 几 MB | 可能几 GB | 复制/移动/校验必须有进度与取消 |
| 缩略图 | 字体自己渲染（无解码） | 必须解码外部文件 | 全项目最重的新代码 |
| 预览可信度 | 100% | 有「合法失败」 | 失败态要设计成一等公民 |
| 索引可重建 | 重扫很快 | 重扫是分钟级 | 「重建索引」必须慎用并提示代价 |
| 平台差异 | 字体加载有库 | 缩略图差异大 | 薄层抽象要更早做 |
| 布局 | 卡片/列表/样张 | 瀑布流/网格/列表 | 瀑布流是新的虚拟化算法，别照抄列表的 |

### 10.2 术语

| 词 | 含义 |
|---|---|
| 库（Library） | 一个被索引的根目录集合，一个库一个 DB |
| 资产（Asset） | 库里的一条素材记录，不含字节 |
| 智能文件夹 | 保存下来的查询条件，动态求值，不复制文件 |
| keyset 分页 | 用「上一页最后一条的排序键」翻页，替代 OFFSET |
| justified 布局 | 行内等高、按宽高比分配宽度的瀑布流算法 |
| 索引式库 | 文件留在原地，只建索引（本方案默认） |
| 托管式库 | 导入时把文件复制进库目录（Eagle 做法） |
| TEST block | `.blend` 文件里存预览图的块 |
