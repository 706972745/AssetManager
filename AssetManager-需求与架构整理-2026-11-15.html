0. 一页速览

问题结论
能不能做能。 底盘、封装、发布、多语言、插件系统、UI 规范全是 FontManager 现成的，新写的只有「索引 + 缩略图管线 + 素材语义」
定位对标 Eagle：标签 + 文件夹 + 智能文件夹 + 瀑布流 + 拖拽 + 采集。差异化只有一条：百万级仍然 60 帧
主场风险Eagle 是 Electron + 每素材一个目录 + 每素材一个 metadata.json，这是它在十万级就开始吃力的结构性原因。我们要赢就必须在结构上换一套，不是把 Eagle 抄快一点
第二风险「流畅」不只是帧率。百万级下真正杀死手感的是：缩略图闪白、布局跳动、筛选卡 1 秒、批量操作没有进度、搜索要等半秒（§5.2）

最省力的地方复用 FontManager 的安装器路线 C、更新链路、签名、9 语言、插件系统、BlinkCaretInput、图标工艺、UI 令牌、本地 HTTP API + 令牌机制（浏览器采集插件直接能用）
工作量单人全职约 15 周到 M4 可发布；M0+M1（百万级能流畅用）约 7 周
最先该做的事①用 Eagle 跑一份 100 万库的性能基线（§5.3）②定 §4.2 的 schema ③拍 §9 的七个问题

1. 讨论还原

四轮问答，主线是一条：「怎么保证不卡、不涨、不崩」。按轮次还原核心主张，最后统一批注。

1.1 第一轮 · 怎么保证用起来不卡

原结论一句话：Rust 负责「看」和「算」，WebView 只负责「画」。五根支柱：

  1. 图片缩略图三级缓存
  2. 一级：Windows 原生缩略图（IShellItemImageFactory），Explorer 看过的图可能直接命中，零解码
  3. 二级：自建持久缓存，key = sha256(路径 + mtime + 尺寸)，容量上限 + LRU
  4. 三级：只预取视口附近（约 ±1 屏），绝不整目录预生成
  5. 缩略图字节不走 IPC：Tauri IPC 会把 Vec 序列化成 JSON 数字数组，5 MB 图能膨胀成 20 MB JSON 直接卡死。改注册自定义协议（thumb://），前端 直取，解码交给 WebView 合成线程
  6. Blender 不启软件拿预览：.blend 内部有 TEST block 存了预览图，解析文件块即可取出，参考 Go 的 blendpreview
  7. 虚拟滚动是底线：只渲染视口内 20–50 个节点，10 万条列表可稳定 59.7 FPS
  8. 元数据进 SQLite 不进 JSON：JSON 在万级就成瓶颈，SQLite 百万行 B-tree 查询亚毫秒

1.2 第二轮 · 多平台化

  • Tauri 2 本身就是跨平台基座，Rust 核心逻辑天然复用
  • 最大坑是缩略图：thumb-rs 支持 macOS（QuickLook）与 Windows（IShellItemImageFactory），不支持 Linux
  • Linux 只能自建管线（libvips / image crate），因为桌面环境碎片化，没有统一系统 API
  • 应对：定义 ThumbnailProvider trait，每平台一个实现，业务层不感知
  • .blend 解析是纯 Rust（blend / blend-rs），零系统依赖，最省心
  • 文件监听用 notify，但路径规范化（大小写、分隔符、Unicode）仍需抽象成 FileSystemAdapter
  • 移动端建议暂缓

1.3 第三轮 · 缓存占多少空间

  • 10 万文件：256px 缩略图 ≈ 1.5 GB，512px ≈ 4.5 GB，SQLite 元数据 ≈ 30 MB
  • 三件套：容量上限 + LRU 淘汰 + 按需生成
  • 元数据不参与淘汰（删了要重扫，代价高），只有可再生成的二进制缓存才淘汰
  • 默认上限建议 1–2 GB，用户可调

1.4 第四轮 · 百万级

  • 存储不是主要矛盾，扫描策略、深分页查询、缩略图限流才是
  • SQLite 必须显式配置：WAL / synchronous=NORMAL / cache_size=-64000 / 四个索引
  • 分页用 keyset pagination（WHERE id > ?），OFFSET 深翻会越来越慢
  • 文件夹树与文件列表分开存：树只存目录节点，列表按 parent_dir 查
  • 首扫必须后台、可中断、可增量、只入元数据不生成缩略图
  • 三个坑：inotify watch 上限（别递归监听全库）、路径索引磁盘开销、扫描与浏览的磁盘 IO 争抢

1.5 我的批注（讨论没说到的地方）

#讨论的说法我的修正
1「第一次扫描百万文件元数据几分钟入库」偏乐观。NTFS 枚举 100 万条目在 SSD 上约 2–6 分钟、机械盘 10–30 分钟，再叠加每文件一次 stat。要按「分钟级 + 可中断 + 断点续扫」设计，别向用户承诺秒级
2「用 thumb-rs 走系统快车道」系统缩略图质量不可控（很多格式拿到的是 96×96 位图），且只在 Explorer 看过才有。它只能当「先出图占位」的一级，不能当最终质量
3「3D 用 LOD 渐进加载」混了两种东西：.blend 不可能交互预览（没有运行时），glTF 可以。两者要分开承诺（§2.5）
4「.blend 里嵌了缩略图」只说了一半。①只有保存时勾了 Save Preview Images 才有；②尺寸通常 128×128；③3.0+ 默认 zstd 压缩，要流式解压到 TEST block。所以「128px 放大＝模糊」是常态，界面要把它设计成正常态
5全程只有「快」，没有「素材语义」对标 Eagle 之后这条更致命：Eagle 的手感 80% 来自标签 + 智能文件夹 + 瀑布流 + 拖拽，性能只是它的短板。只做快 = 没有人搬家的理由（§2.2）

2. 可行性评估

2.1 结论

技术上完全可行，而且成本比想象低；难点从「定位」转移到了「两件硬仗」：

  1. 百万级流畅 —— 结构性工程，不是调参数
  2. Eagle 手感还原度 —— 标签/智能文件夹/拖拽/采集这四件事，缺一件用户就觉得「不如 Eagle」

我上一版说「最大风险是定位」，现在定位拍死了（对标 Eagle），所以风险清单换成上面两条。这不是好消息也不是坏消息，只是把仗打到了正确的地方。

2.2 Eagle 拆解：它凭什么好用，又为什么在百万级会卡

对标要知道对手的结构，否则容易抄错东西。

它凭什么好用（这些必须抄，抄的是体验不是实现）

能力为什么关键
瀑布流（justified，行内等高、按宽高比排）素材浏览的唯一正确布局。等高网格会把竖构图压扁，视觉判断失效
标签（多标签 / 标签组 / 颜色标签）素材的第二套坐标系。文件夹只能套一层，标签能交叉
智能文件夹（保存的查询）整理一次，永远有效。这是 Eagle 最被低估的功能
拖拽到 PS / AI / Blender素材库的出口。没有出口的库是坟墓
浏览器插件采集让「入库」成本降到一次点击，库才长得起来
评分 / 注释 / 来源 URL / 颜色筛选找回素材的 4 条捷径

它为什么在百万级会卡（社区常见反馈 + 结构推断，需实测复核）

结构性原因后果我们的对策
Electron 渲染进程 + 每素材一个 .info 目录（约 3 个文件）100 万素材 ≈ 300 万小文件，NTFS 枚举、杀软扫描、备份、同步全部变慢索引式为主：文件留在原地，库里只有一个 DB + 集中缩略图（§2.3）
每素材一个 metadata.json，启动/切换依赖大量小文件读取首屏随库增大线性变差元数据全在 SQLite 单文件，首屏只查一页（§4.2）
JSON 全量加载进内存十万级就开始吃 1 GB+分页 + keyset，内存恒定 200–500 MB（§5.1）
缩略图生成与 UI 同进程抢资源导入时整机卡住Rust 侧独立线程池 + 优先级队列 + 限流（§4.4）
一句话：Eagle 的库结构是为「可迁移、可手动管理」设计的，不是为百万级设计的。 我们不能既抄它的目录结构又要求它快。
注意：上表是结构推断，开工前必须用 Eagle 实测一份基线（§5.3），否则我们的「更快」没有分母。

2.3 库结构：索引式 vs 托管式（第一个必须拍的决定）

索引式（推荐默认）托管式（Eagle 同款）
文件在哪留在用户原有目录，库只存索引导入时复制进 .library/images//
百万级代价1 份文件 + 1 个 DB + 集中缩略图2 份文件 + 300 万小文件
迁移成本零（不搬文件）大（导入要等几小时）
手动管理用户在 Explorer 里改了，我们靠 mtime 跟上库目录不能乱动
换软件随时走，文件本来就在原地得导出
缺点文件被外部改名/移动后要重定位库是黑盒，但对普通用户更省心

我的建议：索引式做默认，托管式做成「Eagle 兼容模式」给要迁移的人。 理由很直接：你的主场是百万级，托管式在这个量级上是自找的（存储翻倍 + 小文件灾难）。

2.4 真正的难度排序

难度事项为什么难什么时候必须解决
★★★★★百万级流畅（帧预算 / 调度 / 长任务切分）每一处「顺手写」都会在百万级放大成卡顿；要全程有性能纪律M0 就定死，后期补不回来

2.5 三个必须提前承认的天花板

写进 PRD，也写进「关于」页，避免以后被当成 bug：

  1. .blend 只能静态预览，不能交互。

原因：Blender 运行时不可嵌入，几何是 DNA 结构化的内存镜像，不含可渲染场景描述。 能做：TEST block 缩略图（≤128px，可能没有）+ 文件头元数据（版本、是否 packed）。 真做交互预览只有两条路，都贵：调 Blender CLI 导出 glb（要求用户装 Blender），或自研 DNA 解析器（半年起）。

  1. 重格式预览有成本上限。 PSD（合成图可读、图层要额外解析）、AI（PDF 兼容流）、Sketch（zip + JSON，可读）、Figma（需 API）—— 成功率不会是 100%，目标 ≥ 95% 且失败有明确图标。
  2. 首扫是分钟级。 100 万条目枚举 + stat，SSD 2–6 分钟、机械盘 10–30 分钟。UI 上要显示「已扫 43 万 / 预计还需 3 分钟」，而不是转圈。

2.6 明确不做的（省返工）

  • ❌ 抢系统图片默认关联（装完改掉用户双击行为 = 卸载理由）
  • ❌ 移动端（文件系统模型不同，收益低）
  • ❌ 素材编辑（不裁剪不转码成第二个产品；单条导出/转换可以）
  • ❌ 全库递归实时监听（百万级必爆 watch 上限，改「活跃目录监听 + 定时增量」）
  • ❌ 云同步 / 团队协作（现阶段不做，schema 留 owner / updated_at 以便日后加）

4. 架构方案

4.1 分层

│  │ 扫描/监听 │ SQLite   │ 管线/队列 │ 引用/去重  │  │

铁律四条（前三条来自讨论，第四条是我加的，百万级必须）：

  1. 字节永不走 IPC，只走自定义协议
  2. 重活永不进 UI 线程，也不进 WebView 的 JS 主线程
  3. 索引是派生数据，任何时刻可删可重建，真相在文件系统
  4. 任何前端操作都不许「一次查全库」 —— 查询必须带 limit，渲染必须有窗口，批量必须分片

为什么 trigram：素材名大量中文且常被「中间截取」搜索（搜「贴图」要命中「石材贴图_04」）。trigram 支持任意子串，代价是索引体积 2–3 倍 —— 百万级可接受，换来「搜得到」这个最基本的能力。

4.2.1 分页（keyset，不用 OFFSET）

-- 第一页
SELECT id, name, ext, kind, width, height, thumb_key FROM assets
WHERE missing = 0 AND kind IN (?1) ORDER BY mtime DESC, id DESC LIMIT 200;

-- 下一页（带上一页最后一条的排序键）
SELECT ... WHERE (mtime, id) < (?1, ?2) AND ... ORDER BY mtime DESC, id DESC LIMIT 200;

前端永远只持「当前页 + 预取页」（200–500 行）。深翻第 500 页与第 1 页耗时同量级，这是 OFFSET 做不到的。

4.2.2 计数不能每次都 COUNT

侧栏「共 128 万」COUNT(*) 在百万级要几百毫秒到几秒。对策：

  • 维护 meta 表存近似计数（扫描时累加），显示 ≈128 万
  • 精确计数只在用户点开某一分类时算，且结果缓存（counts.version 失效即重算）
  • 前端显示带 ≈ 是诚实做法，比转圈 3 秒好

4.3 扫描层

要求实现
后台独立线程 + scan://progress 事件；前端 3px 进度条 + 「已扫 N / 预计还需 M」+ 取消
可中断AtomicBool 每 500 条检查；取消后已入库数据保留
断点续扫dirs.scanned_at 与 mtime 比对，只重扫变化目录
防环记录 (volume_serial, file_id)，跳过 junction / symlink 回环（Windows 上很常见）
长路径一律 \\?\ 前缀（>260 字符），std::fs 在 Windows 需显式加
写库节奏500 条一个事务 commit，别一条一 commit（百万级会慢 10 倍以上）
IO 谦让扫描线程降优先级；缩略图生成限流；避免用户感觉「硬盘被吃满」

扫描顺序：广度优先（先让用户看到目录结构），并允许「先扫这几个目录」的手动优先队列。

监听：notify 只挂当前展开目录 + 库根，其余靠定时增量（默认 30 分钟或手动）。

管线（「不卡」的真正实现）

   ↓

   ↓

缓存布局

  • key = xxh3(路径 | mtime | size | spec_version | px) → 16 字节 hex
  • 路径：/cache/thumbs/<前2>/<后2>/.webp（两级分桶，避免单目录百万文件）
  • 尺寸只两档：256（列表/瀑布流）与 512（详情，按需）
  • WebP q=78：256px 约 12–18 KB，512px 约 40–60 KB
  • 上限默认 2 GB，LRU 按 last_access（记在 DB 小表，别读文件 atime，不可靠）
  • 到 90% 后台清到 70%，不阻塞前台

三态占位（手感的另一半）

态显示
排队中骨架块（2% 墨底）+ 右上角类型小标，占位尺寸已按真实宽高比算好（不跳行）
低清已出（fast 路径）低清图 + 4px 模糊，高清到位原地替换（不闪白）
失败格式图标 + 弱色「无法预览」，右键可重试
「不闪白」和「不跳行」这两条，比多 10 帧更影响「流畅」的主观感受。

4.5 传输层 thumb://

  • Tauri 2 自定义协议；Windows 上落在 http://thumb.localhost/?s=256
  • 响应头 Cache-Control: public, max-age=31536000, immutable，让 WebView 再缓存一层（免费第四级）
  • 只接受 hex key，不接受任意路径（防穿越）
  • 未命中返回 404 + 触发后台生成；前端 换骨架，绝不同步等生成

4.7 3D / 重格式（M4，不是主场）

.blend 要点（要用时的全部知识）

项内容
魔数前 7 字节 BLENDER
指针宽度第 8 字节 _ = 4 字节，- = 8 字节
字节序第 9 字节 v = 小端，V = 大端
版本第 10–12 字节，如 405
压缩gzip 头 1F 8B（旧）或 zstd 头 28 B5 2F FD（3.0+）
块头code(4) + len(4) + old_ptr(4/8) + sdna(4) + count(4)
预览块code == "TEST"：width(4) + height(4) + RGBA 原始像素（自下而上，要翻转）
  1. 读头 12 字节判断压缩与指针宽度
  2. 压缩文件流式解压，读到 TEST 就停（.blend 常几百 MB 到几 GB，不能整文件解压）
  3. 尺寸常 128×128；放大到 256 用 Lanczos，接受模糊，别标「高清」
  4. 没有 TEST → thumb_state = unsupported，显示格式图标，不重试
  5. 只读 header + TEST + 大小，不解析 DNA

4.8 崩溃安全与可重建

FontManager 的 state.json 事故（1.7 MB 被写回 16 KB）在 DB 上更致命，开头就定死：

  1. DB 是派生数据：删了只丢标签/评分/收藏，文件不动 → 设置页必须有「重建索引」，文案讲清代价
  2. 坏库改名留证：index.corrupt-.db 保留，不静默删
  3. 退出时 PRAGMA wal_checkpoint(TRUNCATE)
  4. 用户创造的数据单独备份：tags / asset_tags / collections / note / rating 每 24 小时导出 userdata-.json（几十 KB），DB 挂了能回灌
  5. 扫描中断标记：scan_incomplete=1，下次续扫而不是重置

8. 路线图

单人全职估，含自测与文档。排序原则：性能地基先于功能，因为性能是结构问题，功能可以后加。

阶段内容估时验收
M0 流畅地基Tauri 2 骨架（照搬 FontManager）；设计令牌共享包；SQLite + migration；扫描器（元数据、可中断、断点续扫）；瀑布流/网格/列表 + 虚拟滚动；thumb:// + 图片缩略图管线；BlinkCaretInput；帧预算与性能埋点3 周100 万库：滚动 ≥55 FPS、闪白 0、跳行 0、首屏 ≤800ms
M1 Eagle 手感标签（含组/颜色）+ 文件夹 + 智能文件夹 + 评分/注释/来源 + 搜索（FTS5）+ 筛选（类型/颜色/尺寸）+ 排序 + 详情 + 批量（可撤销）+ 回收站 + 拖入/拖出 + 缓存设置4 周可当日常素材库用一整天不烦；能替代 Eagle 的日常路径
M2 采集与互操作浏览器采集扩展（复用本地 API）+ Eagle 库迁移 + 重格式预览（PSD/AI/PDF/Sketch）+ 重复/相似检测 + 色板与颜色搜索 + 命令面板3 周采集→入库→找到→拖出，全链路闭环
M3 大库工程化百万级实机压测与调优；多库；自动标签规则；缓存预算打磨；崩溃恢复演练；安装器路线 C + 9 语言 + 插件系统 + 更新 + 签名2 周对外可发布；压测报告达标
M4 扩展.blend 嵌入预览 / .glb 离屏渲染；引用关系与丢失检测；批量重命名；跨平台（macOS 优先）3 周3D 库可出图；引用问题可一键回答

M0 之前必须先做（不做就是挖坑）：跑 §5.3 的 Eagle 基线、定 §4.2 的 schema、拍 §9 的七个问题。

差异FontManagerAssetManager影响
