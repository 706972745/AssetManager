0. 已定的六个决策

#决策结论理由
1库结构索引式（文件留在原地，只建索引 + 集中缩略图）百万级省一倍存储和 300 万小文件；换软件随时走
2视觉沿用 FontManager（纸墨 + 单一蓝 + 0 圆角 + 发丝线 + 自绘块光标）不重学、两软件是一家人
3拖拽出去拖的是缩略图，出去的是原文件（CF_HDROP）产品成立的底线，也是 Eagle 最对的一个设计
4格式所有图片后缀全入库（含小众）；PSD / 3D 预览后期以插件声明接入入库和出图是两件事，先分开
5视图只做两个：常规网格（小/中/大三档）+ 瀑布流；列表后置三个视图＝三套虚拟化和三份 bug
6文件夹1:1 映射真实磁盘：软件里改结构 = 磁盘上真的改无黑盒、不丢东西、与资源管理器双向一致

一句话概括本期目标：

能建库、能秒看、能拖进 PS、能真的整理文件夹。

四件事。标签、智能文件夹、去重、采集插件全部后置。

1.1 做（M0 = MVP）

1.2 不做（本期明确砍掉，别顺手加）

砍掉理由
标签 / 智能文件夹 / 评分 / 注释 / 颜色筛选下一期。文件夹是物理层，标签是虚拟层，先把物理层做实
导入复制（托管式）索引式够用，复制是双倍存储
重复检测 / 相似图依赖全量 hash，属于后台补全任务
浏览器采集插件价值高但要做扩展 + 配对流程，M2
PSD / AI / 3D 预览走插件，不进主程序
列表视图（表格）三个视图会把虚拟滚动的三套实现都写一遍
多库、命令面板、设置面板（除了两行）用不上
批量重命名（规则式）MVP 只做单选重命名；批量等目录操作验证稳了再说
云同步 / 团队不做，schema 留字段即可

判断标准：如果一个功能不能帮「更快看到图」「更快拖出去」「更顺手整理文件夹」，本期不做。

2. 核心方案一：拖出去的是原文件

这是全项目最脏的一块，也是产品能不能立住的唯一开关。开工第一天就要 spike。

2.1 为什么不能直接拖

WebView 里拖一个 ，浏览器塞进拖拽数据对象的是 text/uri-list、text/html，有时加一张 PNG 位图。Photoshop 收到这些只会粘贴一张位图，永远不会去打开文件。

要让它「打开原图」，数据对象里必须有 CF_HDROP（文件路径列表）——Windows Shell 的「拖文件」标准格式，PS / AI / Blender / Explorer 都认它。

结论：不能用 HTML5 拖拽，必须从 Rust 侧发起原生 OLE 拖拽。

2.2 做法（Windows / Tauri 2）

JS                           Rust（UI 线程）
──                          ─────────────
pointerdown  记起点
pointermove  超 5px 且按住左键
  → invoke('start_drag', ids)
                            1. 查 DB 拿真实 path，校验存在
                            2. ReleaseCapture()          ← 把鼠标还给 OLE
                            3. 构造 IDataObject：
                                 SHParseDisplayName → PIDL × N
                                 SHCreateShellItemArrayFromIDLists
                                 SHCreateDataObject(...)       → CF_HDROP
                                 额外再塞 PNG，给不认文件的软件降级
                            4. DoDragDrop(do, src, COPY, &effect)  ← 模态循环
                            5. 返回 effect，前端按需 toast

三条实现纪律

纪律原因
start_drag 必须 run_on_main_thread 后立刻返回，不能 await 拖拽结果DoDragDrop 是模态消息循环，跑到用户松手才结束。JS 等它 = 界面死锁
拖拽前 ReleaseCapture()WebView2 在 pointer 事件里已抓鼠标，不还回去 OLE 拿不到
HTML 侧彻底关掉原生拖拽draggable={false} + img { -webkit-user-drag: none } + onDragStart={e => e.preventDefault()}

2.3 必须处理的边界

情况处理
文件已被移动/删除拖前逐个 exists 校验，缺失的剔掉并 toast「N 个文件已不在原位置」
多选拖拽CF_HDROP 天然支持多文件；上限 50 个（更多会把对方软件卡住）
拖拽语义一律 DROPEFFECT_COPY，不提供 MOVE。避免用户误以为在移动文件
拖到不支持文件的软件额外提供 PNG 位图降级，至少能贴图
拖拽期间界面前端不跑动画（模态循环会吃掉一帧）
松手后SetForegroundWindow 回主窗口，否则焦点留在对方软件

2.4 Spike 验收（2 天，不通过就换方案）

  1. 拖 1 张 jpg 到 Photoshop → PS 打开原图（不是粘贴位图）
  2. 拖 3 张到资源管理器 → 复制出 3 个文件
  3. 拖 1 张到 Chrome 地址栏 → 出现 file:///...（证明 CF_HDROP 生效）
  4. 拖拽中界面不冻结，松手后能立刻继续滚动
  5. 拖拽时文件已删 → 有 toast，不崩溃

退路：①右键「复制文件路径」+「在资源管理器中显示」保底；②用成熟 crate 的隐藏窗口方案；③不做「先复制到临时目录再拖」（破坏原文件语义）。

3. 核心方案二：文件夹就是磁盘（1:1 映射）

3.1 原则

软件里的树，就是磁盘上的树。零虚拟层。
  • 库里没有「导入」概念（索引式），所以不存在「库内副本」与「磁盘文件」两套东西
  • 用户在软件里新建/重命名/移动/删除 → 磁盘上真的发生
  • 用户在资源管理器里改了 → 软件跟着变（监听 + 增量扫描）
  • 唯一的虚拟层是标签（M1 起），它不改文件夹、不复制文件

3.2 为什么这个决定是对的

好处说明
不会丢东西文件永远在原本位置。软件崩了、卸载了、数据库删了，素材一个不少
没有黑盒备份、同步、Git、杀软、Everything 全都能用现成方案
双向一致与资源管理器、Finder、命令行共用同一份真相，不用「导入/导出」搬运
心智模型零成本用户不用学「库」和「文件夹」的区别，它就是你的磁盘，只是看得更快

代价只有一条：误操作是真的。 所以 §3.5 的撤销、§3.6 的索引纪律、§3.8 的确认阈值不是可选项，是这套方案能成立的前提。

3.3 操作清单与实现

操作系统调用细节
新建文件夹CreateDirectoryW重名自动 新建文件夹 (2)；输入时先过滤非法字符
重命名文件MoveFileExW（同目录）只改大小写 → 两步（先改临时名再改回），否则 NTFS 认为同名不动
重命名文件夹MoveFileExW + 一条前缀 SQL不遍历文件，只更新 dirs.path（见 §3.7）
移动（同盘）MoveFileExW本质是 rename，瞬时、原子
移动（跨盘）复制 → 校验 → 删源有进度、可取消；中途失败保留源，不留半个文件
删除IFileOperation（系统回收站）可恢复。Shift+Del 真删，且二次确认
在资源管理器中显示SHOpenFolderAndSelectItems兜底入口，必须有

3.4 冲突与异常（都必须有明确文案，不许静默）

情况处理
目标同名不覆盖。弹「保留两者 / 替换 / 跳过」。保留两者自动加 (2)
非法字符 \ / : * ? " < > \|输入时就拦，红色提示，不允许提交
系统保留名 CON PRN AUX NUL COM1–9 LPT1–9同上，拦在输入层
名字结尾是空格或点自动去掉（Windows 会静默丢弃，导致「改名了但没变」）
路径超过 260 字符一律 \\?\ 前缀
文件被占用（PS 正开着）失败并提示「文件正被 Photoshop 使用」，不重试、不崩溃
只读 / 无权限明确提示「没有权限修改这个文件夹」，不做静默降级
把目录移进自己的子目录前置校验直接拒绝（经典 bug，会造成无限递归）
目标在网络盘 / 另一块慢盘允许，但提前提示「跨盘移动会复制文件，可能需要时间」

3.5 撤销（高危操作的唯一保险）

真实文件操作不能没有撤销，否则用户迟早恨你。

  • 每次操作写 ops 表：id / kind / ts / payload_json / undone
  • payload_json 记每个文件的 from 与 to，撤销 = 逆向执行
  • 只保留最近 20 次（表定长，超了删最旧），入口：Ctrl+Z + 底栏「已移动 42 个文件 · 撤销」
  • 跨盘移动的撤销 = 反向移动（可能又跨盘，慢，要提示）
  • 删除的撤销 = 从回收站还原（尽力而为；失败如实说「回收站里已找不到，请手动恢复」）
  • 撤销失败要给原因，不能假装成功

3.6 索引同步纪律

铁律：以文件系统为准，操作后 re-stat，不靠推算。
时机做法
操作前校验（存在性、权限、目标空位、非自己子目录）
操作成功事务内更新 DB：dir_id / name / 新建 dirs 行
操作失败DB 不动，用户看到的仍是真实状态
DB 写失败（罕见）标记该目录 needs_rescan，后台重扫一次 —— 最终一致的兜底
外部改动notify 监听活跃目录 + 库根（不递归整库）+ 启动时增量扫描（dirs.mtime 比对）
缩略图 key见下方「移动后不该重新生成」

移动后不该重新生成缩略图 —— 这是最容易忽略、用户最容易察觉的一处劣化。

如果缓存 key 里含完整路径，「把 3000 张图挪进子目录」会让 3000 张缩略图全部失效重生成，用户看到的是「软件又在扫了」。对策：

  • key 优先用 (volume_serial, file_id, mtime, size, px) —— Windows 上 file_id 在重命名/移动后不变
  • 拿不到 file_id（网络盘 / FAT32 / 某些虚拟盘）时，退化为 path 哈希
  • 两种 key 都写进 thumb_key，换算法不影响旧缓存

3.7 目录重命名的成本（一个 SQL，不是遍历）

assets 表只存 dir_id + name，不存完整路径。所以：

  • 重命名文件夹 → 改一行 dirs.name + 前缀替换 dirs.path：
  UPDATE dirs SET name = ? WHERE id = ?;
  UPDATE dirs SET path = ? || substr(path, length(?) + 1)
  WHERE parent_id != id AND path LIKE ? || '%';
  • 移动文件夹 → 同理，改 parent_id + path 前缀
  • 百万素材的库，重命名顶层文件夹 ≈ 几百行 dirs 更新，毫秒级，不碰 assets 一行

完整路径只在需要时由 dirs.path + assets.name 拼出来（打开、拖拽、复制路径）。

3.8 两种拖拽语义（必须区分清楚）

同一个「拖」手势，落点不同，行为完全相反：

手势落点语义实现
拖格子库内（目录树节点）移动（真实改 dir_id，落盘）HTML5 DnD + fs_move
拖格子库外（PS / Explorer / 桌面）导出原文件（复制出去，源不动）pointer + Rust DoDragDrop + CF_HDROP

MVP 的取舍：内部移动只允许落到「目录树节点」。 拖到网格空白处不触发移动。

理由：真实移动是高危操作。落点明确、有高亮、最多错一层目录 —— 这个约束比「多一个更方便的入口」值钱得多。等目录操作验证稳了，M2 再支持「拖到另一个文件夹的网格区域」。

阈值确认（不是每次都弹，只在越线时弹）：

触发行为
移动 > 100 个文件二次确认：「将 3,241 个文件移动到 素材/旧/？」
移动总大小 > 2 GB二次确认，并提示跨盘会复制
删除 > 20 个文件二次确认，并说明「送进回收站，可恢复」
删除整个文件夹二次确认 + 显示子项总数

3.9 目录树规格（.tree）

元素规格
位置左侧栏，宽 240，可拖 200–360，可收起
数据懒加载：展开才查子目录，一次 ≤ 200 条（百万级库目录也可能上万）
行高 32 / 0 圆角 / 11px / 次文字色；悬停 --ui-hover；选中 = 纯底色 + ::before 2×32 蓝竖线

4. 核心方案三：所有图片后缀入库

4.1 一条原则，两个独立能力

「能识别」和「能出图」是两件事。
  • 入库：任何扩展名都收（甚至无扩展名，靠文件头嗅探）。入库 = 有记录、有尺寸、有类型图标
  • 出图：尽力而为。出不了不是错误，是「这种格式暂时没解码器」

这条原则直接回答「适配所有图片后缀」：正解是全部入库 + 分级出图 + 明确失败态，而不是「不支持就不显示」。后者会让库看起来「少了文件」，是最糟的体验。

4.2 五级解码链（按顺序尝试，命中即停）

级手段覆盖格式速度
L1Rust image crate（纯内存，无系统依赖）png / apng / jpg / jpeg / gif / webp / bmp / ico / tif / tiff / tga / dds / exr / hdr / pnm·pbm·pgm·ppm / qoi / farbfeld / avif / jxl快
L2Windows WICheic / heif（需 HEIF 扩展）/ jxr / wdp / hdp / RAW（cr2 nef arw dng，需 RAW 编解码器）/ wmf / emf中
L3系统缩略图 IShellItemImageFactory任何装了缩略图提供者的格式（PSD / AI / CLIP / 第三方插件）快，质量不可控
L4插件（后期）PSD / PSB / AI / Sketch / blend / glb / fbx …慢，走队列
L5失败类型图标 + 弱色「暂无预览」—

L3 命中的图标记 thumb_quality = low，详情面板如实显示「系统预览」。

            "qoi","ff","avif","jxl","jp2","heic","heif","jxr","wdp","hdp",
            "cr2","cr3","nef","arw","dng","raf","orf","rw2","srw","pef",
            "psd","psb","ai","eps","svg","sketch","clip","xcf","wmf","emf"],
    "thumb": ["L1","L2","L3"],
    "badge": "IMG"
  }
}

psd / ai / svg / sketch / clip / xcf 也放进 image.ext：先入库、先显示类型图标，等插件来了再出图。这就是「先做基础，后续插件适配」的落地方式。

4.4 扫描阶段只读文件头（关键性能点）

百万级扫描绝不能解码图片。但瀑布流需要宽高比才能不跳行。

做法：只读头部 64 KB 解析尺寸，不解码像素。

格式尺寸所在
PNGIHDR chunk 第 16–23 字节（big-endian）
JPEG遍历 FFxx 找 SOF0/1/2/9/10：高 2 字节、宽 2 字节
GIFLogical Screen Descriptor 第 6–9 字节（little-endian）
WebPVP8X / VP8 / VP8L 三种分支
TIFFIFD 里 tag 256 / 257
BMPBITMAPINFOHEADER 宽高各 4 字节
其他image::io::Reader::with_guessed_format().into_dimensions()（只读头）

收益：扫描不会被解码拖垮，而瀑布流手里已有宽高比 → 不跳行从第一帧就成立。

4.5 文件头嗅探（纠正错误扩展名）

.png 其实是 webp、.jpg 其实是 psd 很常见（下载工具改名）。读前 16 字节比魔数，以真实格式为准，扩展名只作提示。

FF D8 FF = jpeg，89 50 4E 47 = png，47 49 46 38 = gif，52 49 46 46…57 45 42 50 = webp，49 49 2A 00 / 4D 4D 00 2A = tiff，44 44 53 20 = dds，76 2F 31 01 = exr，38 42 50 53 = psd，25 50 44 46 = pdf，71 6F 69 66 = qoi。

6.3 三档缩略图与小/中/大的真实含义

档格子边长（CSS px）取源像素缓存档位单张 WebP适用
小120240256~15 KB快速扫一遍、大库找图
中176352384~30 KB默认档
大260520512~50 KB看构图、挑素材

「前提是文件本身分辨率够」这条，落成四条规则：

#规则说明
R1取源 = min(缓存档位, 原图长边)永不放大。原图 300px 就按 300 出
R2永不从低档缩略图当高档的源大档必须重新从原图解码。从小到大放大＝糊两次，这是素材工具最常见的劣化
R3原图长边 < 档位 × 0.75 → 标记 upscaled图照常显示，但详情面板如实写「原图 800 × 600 · 接近原尺寸显示」，不假装高清
R4DPR 变化不触发重新生成档位像素固定，DPR 只影响显示精度上限。否则窗口拖到 150% 缩放的显示器就全库重生成

R2 的代价：切档要重新解码。所以切档时只优先生成视口内的，其余进后台队列；已有大档的可直接缩成小档用，反之不行。

6.4 常规网格（.view-grid）

元素规格
布局正方形格 aspect-ratio: 1，间距 8，行高 = 格宽
缩略图object-fit: cover（裁切填满；细节交给空格预览）
虚拟化按行：cols = floor((w + gap) / (tile + gap))，只渲染视口 ±2 行
三档切换改格宽 → 重算行列 → 保留顶部锚点项
列数上限大档 ≤ 8 列，小档 ≤ 16 列

6.5 瀑布流（.view-waterfall）

元素规格
算法justified：行内等高 H，按 sum(aspect) 分配宽度；最后一行不拉伸，左对齐
行高随档位：小 140 / 中 200 / 大 280
缩略图object-fit: contain（不裁切，素材要看全）
宽高比来源扫描时读文件头（§4.4）。缺的按 4:3 兜底并标 aspect_unknown，出图后 transition: aspect-ratio 120ms
虚拟化按行（行由 aspect 累加得出，先算行再渲染）
窗口 resize防抖 120ms；宽度变化 > 8px 才重排；重排保留锚点（顶部首个可见项 id + 偏移）
单行格数上限12（防止超宽屏一行铺太散）
瀑布流最容易翻车的不是算法，是重排时丢滚动位置。用户拉一下窗口就跳回顶部，手感立刻崩。

6.6 格子（两视图共用 .asset-tile）

ALTER TABLE dirs ADD COLUMN name          TEXT;               -- 目录名（不含路径）

CREATE TABLE ops (                 -- 操作日志，撤销用，定长 20
  id      INTEGER PRIMARY KEY,
  kind    INTEGER NOT NULL,        -- 0 新建 1 重命名 2 移动 3 删除
  ts      INTEGER NOT NULL,
  payload TEXT NOT NULL,           -- JSON: [{from,to,from_dir,to_dir}]
  undone  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_ops_ts ON ops(ts DESC);

不加 UNIQUE(dir_id, name)：Windows/macOS 大小写不敏感、Linux 敏感，同一约束在三平台语义不同。重复记录由扫描覆盖写处理，不靠约束。
